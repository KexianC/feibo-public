# Digital Doctor 项目架构与模块交接文档

**文档版本: v1.0**

## 1. 项目概述

- **项目名称**: Digital Doctor (数字医生)
- **项目类型**: Spring Boot
- **技术架构**: DDD (领域驱动设计) + 六边形架构
- **Java版本**: 17
- **Spring Boot版本**: 3.4.3

## 2. 整体架构设计

### 2.1 架构模式

项目采用 DDD (领域驱动设计) 和 六边形架构 (Hexagonal Architecture) 相结合的设计模式，旨在实现业务逻辑与技术实现的清晰分离，提高代码的可维护性和可扩展性。

**架构分层图:**

```
┌───────────────────────────────────────────────────────────┐
│                     Trigger Layer (触发层)                    │
│  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐        │
│  │  HTTP API   │   │  Job调度    │   │  Event监听  │        │
│  │  Controller │   │  Scheduler  │   │  Listener   │        │
│  └─────────────┘   └─────────────┘   └─────────────┘        │
└───────────────────────────────────────────────────────────┘
                               │
┌───────────────────────────────────────────────────────────┐
│                      API Layer (接口层)                     │
│  ┌───────────────────────────────────────────────────────┐  │
│  │             接口定义 + DTO + 响应模型                 │  │
│  └───────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
                               │
┌───────────────────────────────────────────────────────────┐
│                     Domain Layer (领域层)                   │
│  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐        │
│  │   业务实体    │   │   领域服务    │   │   业务事件    │        │
│  │   Entity     │   │   Service    │   │   Event      │        │
│  └─────────────┘   └─────────────┘   └─────────────┘        │
└───────────────────────────────────────────────────────────┘
                               │
┌───────────────────────────────────────────────────────────┐
│              Infrastructure Layer (基础设施层)              │
│  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐        │
│  │   数据访问    │   │   外部服务    │   │  缓存/消息   │        │
│  │  Repository  │   │   Gateway    │   │  Redis/MQ   │        │
│  └─────────────┘   └─────────────┘   └─────────────┘        │
└───────────────────────────────────────────────────────────┘
```

## 3. 模块结构详解

### 3.1 `digital-doctor-api` (接口定义层)

- **职责**: 定义对外暴露的API接口和数据传输对象（DTO）。
- **核心组件**:
    - **接口定义**: `I*Api.java` - 定义业务接口契约。
    - **DTO对象**: 请求/响应数据传输对象。
    - **响应模型**: 统一的API响应格式。
    - **验证注解**: 自定义验证规则。
- **主要接口**:``
    - `IAIApi` - AI对话相关接口``
    - `IAuthApi` - 用户认证接口
    - `ITradeApi` - 交易支付接口
    - `IUserApi` - 用户管理接口
    - `ICopywritingApi` - 文案审批接口
    - `IDigitalHumanApi` - 数字人相关接口
    - `IMessageApi` - 消息通知接口

### 3.2 `digital-doctor-trigger` (触发层)

- **职责**: 处理外部请求和事件触发，是应用的入口。

- **核心组件**:

    - **HTTP控制器**: 处理REST API请求。
    - **定时任务**: 系统定时作业。
    - **事件监听器**: 处理异步领域事件。

- **目录结构**:

  ```
  trigger/
  ├── http/            # HTTP API控制器
  │   ├── AIController.java
  │   ├── AuthController.java  
  │   ├── TradeController.java
  │   └── ...
  ├── job/             # 定时任务
  │   └── NoPayNotifyOrderJob.java
  └── listener/        # 事件监听器
      ├── OrderPaySuccessListener.java
      └── RegisterSuccessListener.java
  ```

### 3.3 `digital-doctor-domain` (领域层)

- **职责**: 包含所有核心业务逻辑和领域模型。

- **业务领域划分**:

    - `ai`: AI对话管理
    - `auth`: 用户认证授权
    - `trade`: 交易支付
    - `user`: 用户管理
    - `copywriting`: 文案审批
    - `digital`: 数字人相关
    - `message`: 消息通知

- **各领域目录结构**:

  ```
  domain/{领域}/
  ├── model/           # 领域模型
  │   ├── entity/      # 实体对象
  │   ├── aggregate/   # 聚合根
  │   └── valobj/      # 值对象
  ├── service/         # 领域服务
  ├── adapter/         # 适配器接口（Port）
  └── event/           # 领域事件
  ```

### 3.4 `digital-doctor-infrastructure` (基础设施层)

- **职责**: 提供技术实现和与外部系统的集成。

- **核心组件**:

    - **数据访问**: MyBatis-Plus + MySQL 实现。
    - **外部网关**: 集成第三方服务。
    - **缓存服务**: Redis 操作实现。
    - **配置管理**: 系统配置属性类。

- **目录结构**:

  ```
  infrastructure/
  ├── dao/             # 数据访问对象 (Mapper)
  ├── adapter/         # 适配器实现 (Adapter)
  │   ├── repository/  # 仓储实现
  │   └── port/        # 端口实现
  ├── gateway/         # 外部服务网关
  │   ├── ai/          # AI服务
  │   ├── pay/         # 支付服务
  │   ├── oss/         # 对象存储
  │   └── sms/         # 短信服务
  ├── redis/           # Redis操作
  └── properties/      # 配置属性
  ```

### 3.5 `digital-doctor-types` (通用类型层)

- **职责**: 定义项目范围内的通用工具类和类型。
- **核心组件**:
    - `Constants`: 系统常量定义
    - `Enums`: 业务枚举
    - `Exceptions`: 自定义异常
    - `Utils`: 通用工具方法
    - `Annotations`: 自定义注解

### 3.6 `digital-doctor-app` (应用启动层)

- **职责**: Spring Boot 应用启动和全局配置。
- **核心组件**:
    - `Application.java`: 应用主启动类。
    - `config/`: Spring 配置类。
    - `resources/`: `application.yml` 等配置文件。

## 4. 核心技术栈

- **框架技术**:
    - Spring Boot 3.4.3: 应用框架
    - Spring Security: 安全认证
    - Spring AI: AI集成框架
    - MyBatis-Plus: ORM框架

- **外部服务集成**:
    - 腾讯云: AI对话服务
    - 阿里云OSS: 对象存储
    - 阿里云SMS: 短信服务
    - 通联支付: 支付服务
    - 数字人API: 数字人服务
- **工具库**:
    - Guava: 工具类和EventBus
    - JWT: 令牌认证
    - Lombok: 代码简化
    - Jackson: JSON处理
    - Apache Tika: 文件处理
    - Sensitive-word: 敏感词过滤

## 5. 核心业务流程与模块注意事项

### 5.1 用户注册流程

- **流程**: 用户注册 → 发送验证码 → 验证手机号 → 创建用户 → 绑定默认角色 → 发布注册成功事件 → 绑定默认AI套餐。

### 5.2 AI对话流程

- **流程**: 用户发起对话 → 权限验证 → 消费AI配额 → 调用AI服务 → 敏感词过滤 → 保存对话记录 → 返回结果。
- **⚠️ 注意事项**:
    - 在“深度思考”模式下，Spring AI 的标准接口存在兼容性问题，无法直接流式打印出深度思考的过程内容（尽管数据已传递至后端）。
    - **建议解决方案**: 绕过 Spring AI 的封装，直接使用 HTTP 请求处理流式数据，手动解析并返回给前端。此部分因时间关系未实现。

### 5.3 支付交易流程

- **流程**: 创建订单 → 调用支付接口 → 等待支付回调 → 订单状态更新 → 发布支付成功事件 → 权益发放。

- **⚠️ 注意事项**:

    - 目前系统未处理用户重复购买同一种会员套餐的情况。
    - **建议解决方案**: 增加业务逻辑，可考虑实现“待生效”方案（新套餐在当前套餐结束后生效）或“覆盖”方案（新套餐立即生效并覆盖旧套餐）。
    - 退款功能暂未开发，仅预留了接口位置，可根据未来业务需求决定是否实现。

  **权益回滚逻辑尚未编写**。

  权益明细值 ID 虽然已生成，但是没有时间写后续如果要回滚的话

    - 数字人要多一个资源回滚接口

    - ai问答的话就是多一个存储层的一个函数

### 5.4 文案审批流程

- **流程**: 提交文案 → 分配审批人 → 审批处理 → 状态机流转 → 结果通知。
- **⚠️ 注意事项**:
    - **专家审核目前是写死的**，仅为演示目的。后续需根据明确的需求（专家主动领取任务 或 审批流自动分配）进行重构。
    - 此模块测试不充分，因为后端就一个实习生干审批流不好测试
    - **数字人配音部分未经测试**，因需求变更导致没时间测试

## 8. 安全设计

- **认证授权**:
    - **JWT Token**: 实现无状态认证。
    - **角色权限**: 基于 RBAC 的权限模型。
    - **方法级安全**: 使用 `@PreAuthorize` 注解进行细粒度控制。
- **数据安全**:
    - **敏感词过滤**: 对用户输入内容进行安全检查。
    - **参数验证**: 使用 `jakarta.validation` 对输入数据进行校验。
    - **SQL注入防护**: MyBatis-Plus 框架本身支持预编译，有效防止SQL注入。

## 9. 监控和日志

- **日志配置**:
    - **Logback**: 作为日志框架。
    - **分级日志**: ERROR / INFO 日志分离存储。
    - **文件滚动**: 按日期和大小进行日志文件滚动。
- **异常处理**:
    - **全局异常处理**: `GlobalExceptionHandler` 统一处理未捕获异常，返回标准响应格式。
    - **业务异常**: 自定义业务异常类，明确错误类型。
    - **事件补偿**: 建议为关键的异步事件（如发货、权益发放）增加失败重试或手动补偿机制。

## 11. 最终重要注意事项

- **项目背景**:
  本项目由一名前端和一名后端实习生在一个半月内从零搭建完成。其主要目标是快速上线，实现核心功能。代码虽已尽力解耦，但由于时间紧、任务重、需求频繁变更，部分实现可能较为粗糙，测试覆盖率有限。请将其视为一个功能可运行的“茅草屋”，后续需要持续完善和加固。
- **用户规模**: 目前项目用户量极小（含内部人员不超过10人），性能压力不大，但未来扩展时需考虑性能优化。然后redis也别用算了
  因为这个项目只是为了演示基本上没有人用，但是好处就是这个项目你可以尽情写 怎么难怎么写 可以加一堆中间件模拟高并发场景
  为了简历上有东西写
- **缺点**：
    1. **代码并发混乱**，因为工期很赶 而且就我一个实习生负责 并且这个项目是完全从0开始，开发时间就一个半月，需求都是自己分析没有人帮助
       数据库也是要自己搭建，因为原来项目的数据库有十来张表根本没用的很乱，然后就是原来项目是php开发的 也没有原始代码
    2. **实体建模混乱**：项目用的是DDD架构，实体因为项目太紧就可能会有点乱，就本来应该单一职责拆分的加上需求不明确
       所以很多实体可能共用违反了DDD的要求，
- **EventBus配置**: **（非常重要）**`GuavaConfig` 中需要手动注册所有的事件监听器 (`Listener`)，否则事件发布后将无法被正确消费。
- **循环依赖处理**: 为避免循环依赖问题，部分代码中使用了 `SpringUtil.getBean()` 方式延迟获取Bean。
- **事务管理**: 在处理跨多个聚合根的业务操作时，需特别注意分布式事务的一致性问题。可考虑使用乐观锁来防止并发更新导致的数据不一致。
- **性能优化建议**:
    - 对高频访问的数据增加缓存。
    - 根据服务器规格调优数据库连接池参数。
    - 将非核心、耗时的操作（如发送通知、记录日志）改为异步处理。

## 12. 开发规范

- **代码规范**:
    - 严格遵循DDD设计原则，保持领域层的纯净性。
    - 使用统一的全局异常处理机制。
    - 保持接口定义（API层）和业务实现（Domain层）的分离。
- **测试规范**:
    - 单元测试应覆盖领域层的核心业务逻辑。
    - 集成测试用于验证与数据库、缓存和第三方服务的交互。
